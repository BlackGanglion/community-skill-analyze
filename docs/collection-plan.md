# 社区 Skill 采集与持续更新方案

状态：待确认，尚未实施采集。日期：2026 年 10 月 9 日。

项目目标是建立可追溯、可持续更新的社区 Skill 本地资料库，为后续分类、去重、质量评估和趋势分析提供原始数据。第一阶段以 LobeHub 为发现入口，保存目录元数据、Skill 原文和配套文件；分析功能在采集链路稳定后再开展。

本次交付仅为方案文档。采集程序、首次全量下载和定时更新任务将在方案确认后实现。

## 目标与首期边界

“目前开源社区的所有 Skill”是长期覆盖目标，不能用单一市场的收录量证明已经完成。首期可验证的目标是：**尽可能完整地枚举 LobeHub 可访问目录，将符合采集条件的 Skill 文件保存到 egg-server 本地，并明确列出未获得内容的条目及原因。**

“本地”默认指现有开发服务器 egg-server，项目目录为 `/home/egg/code/community-skill-analyze`。Mac 用于查看文档和结果，首期不维护第二份自动同步的数据副本。

| 对象 | 首期处理方式 |
| --- | --- |
| LobeHub 可枚举的 Skill 条目 | 保存原始元数据、来源链接、版本、观察时间和采集状态 |
| 可公开获取且许可证允许采集的内容 | 下载 `SKILL.md` 及同一 Skill 目录中的脚本、参考资料、模板、资源和许可证 |
| 明确开源的 Skill | 纳入开源分析候选集，保留许可证证据 |
| 非开源、许可证不明确或冲突的条目 | 保留目录记录和状态，默认不进入开源内容集；后续按具体许可决定是否收录内容 |
| 不同市场、不同名称或不同仓库中的同源内容 | 保留各自来源关系，使用内容哈希识别相同版本，不直接删除条目 |
| 登录受限、私有、付费或已失效内容 | 记录缺口，不尝试绕过访问限制 |
| 历史版本 | 首次只取当前版本；从首次采集起保留变化版本，暂不回溯全部历史 |
| Skill 引用的外部网页、依赖和大模型 | 保存引用，不递归抓取外部互联网，不安装依赖、不执行 Skill |

完整包的边界是目标 Skill 的目录及随包文件，不是整个源码仓库。一个仓库可以包含多个 Skill，不能把仓库数当成 Skill 数。

## 采集路径

推荐采用“市场发现条目，源站获取内容，本地保存不可变快照”的流程。

1. **建立目录清单。** 优先通过已验证的官方 Market API 或固定版本的 SDK 获取完整分页结果，保存每页原始响应、参数、总数、页码和观察时间。固定一个 locale，避免多语言页面重复计数。
2. **解析来源。** 保存市场 identifier 和原始来源 URL，解析仓库、分支或 tag、Skill 路径，处理仓库转移和 URL 重定向。不能根据 slug 中的连字符猜测仓库及目录。
3. **确认内容资格。** 记录仓库及 Skill 目录内的 LICENSE、NOTICE、frontmatter 许可声明和市场标签。缺失或相互冲突时标为待确认，不自动认定为开源。
4. **获取内容快照。** 对合格的 GitHub 来源，解析目标 ref 为确定的 commit SHA，取得目标 Skill 完整目录；按仓库和 commit 共享下载缓存。无需为每条 Skill 单独 clone 整个仓库。
5. **处理 Market 包。** 没有可用源码映射但提供可下载且许可明确的发布包时，保存指定版本包。源码与发布包都取得时分别保留，记录关联，不能将它们标成同一个版本。若只能取得网页正文，标为 `text_only`，不算完整下载成功。
6. **校验并入库。** 校验文件边界、根目录、哈希、`SKILL.md` 和文件清单，再写入索引。先写临时目录，校验成功后原子发布快照，避免中断后把半包当成完成。
7. **输出采集报告。** 列出唯一条目数、源码仓库数、开源候选数、完整快照数、内容重复组、失败与排除原因、下载字节数和耗时。

首期保留两种内容口径：`upstream` 表示所声明 ref 在采集时解析出的 GitHub 版本；`market_release` 表示市场发布包版本。市场更新时间、Git commit 时间和本地观察时间分别存储。若市场仅指向分支，“最新版”指本次解析到的 SHA，不能宣称它就是市场发布时的源码。

### 全量枚举与完整性

官方说明中的 `--q` 是可选参数，但无关键词查询、深分页上限、排序稳定性和服务器端总数仍需在真实认证后验证。验证失败时暂停全量阶段，保留已发现清单与阻塞原因。

若接口支持稳定游标或快照，则优先使用；若只有页码，采用验证过的稳定排序，记录扫描开始和结束时间及总数变化，对 identifier 去重，并进行重叠扫描与第二轮对账。重复返回同一页、异常空页、总数骤降或缺页都不能视为完成。

目录在扫描期间持续变化时，只能报告某一时间区间内的观测集合。两轮结果相近可以作为收敛信号，不能证明覆盖了整个社区。分类拆分仅在分类覆盖和分页上限经过验证后使用；搜索引擎结果和热门榜不能作为兜底的全量清单。

官方 API 不可用时，可评估已允许且可访问的公开 sitemap 与详情页。报告必须保留 `enumeration_partial` 状态，不能将备用入口发现的集合当成全站全量。若存在官方导出或批量访问渠道，优先使用。

## 本地保存与数据结构

建议首期使用 Python 采集器、SQLite 索引和普通文件快照。该选择便于服务器运行、断点续传和离线分析；它只是采集模块的建议，不限定后续产品界面或分析服务的技术栈。实施时固定依赖版本，先以单机单写入者运行，避免过早引入队列服务和数据库集群。

代码和文档进入 Git；采集到的第三方内容、数据库、缓存、凭证和运行日志不进入当前公开仓库。建议数据根目录独立于代码检出目录，通过 `DATA_DIR` 配置：

```text
/home/egg/data/community-skill-analyze/
  catalog.sqlite
  raw/lobehub/<run_id>/              # 原始目录和详情响应
  blobs/sha256/<prefix>/<hash>       # 按原始字节去重的文件与包
  snapshots/<skill_id>/<snapshot_id>/
    manifest.json                   # 路径、文件大小、哈希、来源
    files/                          # 可供后续离线分析的完整文件树
  cache/repos/                      # 可回收的仓库下载缓存
  runs/<run_id>/                    # 检查点、统计和脱敏错误
  exports/                         # 可重建的 JSONL 数据集
```

文件树可用硬链接引用同一文件系统中的 blobs；不支持时使用复制。对外提供的快照只读，后续分析产物另存，不能修改原始文件。数据库不是唯一副本：每个快照保留独立 manifest，并定期导出索引。

| 数据实体 | 建议字段与约束 |
| --- | --- |
| 来源条目 `source_entries` | `source`、`identifier` 联合唯一；名称、描述、作者、分类、标签、市场版本、原始 URL、统计值与其观察时间、原始响应位置、首次及最近发现时间 |
| 内容来源 `origins` | 规范化仓库标识、原始和最终 URL、Skill 路径、声明 ref、许可证状态及证据路径；仓库迁移保留别名 |
| 条目与内容关系 `entry_origins` | 保留一条目录记录对应多个来源、多个条目对应同一来源的关系 |
| 快照 `snapshots` | 来源、内容口径、commit SHA 或发布版本、获取时间、包哈希、正文哈希、文件树哈希、解析器版本、完整性状态、manifest 路径 |
| 文件 `files` | 快照、相对路径、类型、大小、原始字节哈希、blob 路径；文件树哈希覆盖排序后的路径和字节哈希，附件变化也会产生新版本 |
| 采集任务 `jobs` | 稳定任务键、状态、尝试次数、下次重试时间、错误分类、租约及检查点；同一任务重复执行不产生重复快照 |
| 运行 `runs` | 类型、起止时间、配置与采集器版本、目录边界、分项计数、流量、完整性结论、上次成功时间 |

缺失字段保存为 null，并与空字符串、0 区分。统计字段不参与内容哈希。市场名称不作为文件路径或唯一主键；路径使用内部安全 ID，原始名称保存在元数据中。

## 持续更新设计

建议首次全量采集完成后，在 egg-server 上由 systemd timer 启动采集命令。以下是计划频率，本次不创建 timer、cron 或 Codex 自动化。

| 周期 | 任务 | 更新策略 |
| --- | --- | --- |
| 每日北京时间 03:00 | 目录变化扫描 | 按 `updatedAt` 倒序读取，覆盖上次成功水位前 48 小时；相同时间戳继续遍历完整边界；只有接口稳定性通过验证后才允许提前停止 |
| 每日 | 内容更新队列 | 优先处理新增和变化条目；按仓库检查目标 ref，SHA 未变化则复用快照；源码检查独立于市场更新时间 |
| 每周日北京时间 04:00 | 全目录对账 | 完整重扫 identifier，发现漏项、来源变化、市场下架和增量扫描遗漏 |
| 滚动七天 | 未变化来源复核 | 对所有可跟踪的仓库 ref 或发布包分批重新检查，防止只依赖市场更新时间而永久漏更 |
| 每周 | 数据保护与恢复检查 | 一致性备份数据库、manifest 与不可变 blobs；备份目的地和容量在实施阶段确定 |

七天复核是待容量验证的目标，不是现阶段承诺。若吞吐不足，报告队列年龄和预计滞后并调整周期，不静默将旧数据标为最新。首次全量持续数天时，应同时登记新增条目，避免首次扫描结束前数据已经大幅落后。

更新任务与首次采集共享同一任务队列和锁，防止重叠运行。上一轮未结束时不再启动第二个全量任务；中断任务恢复租约后继续。目录水位只有在相关记录与后续任务持久化后才能推进，内容下载失败由队列独立重试。

能确认服务端支持时使用 ETag 或 Last-Modified 条件请求；不能用 HTTP 200 或版本字符串未变代替内容哈希校验。相同哈希不重复保存，发生变化时生成新快照并更新“最新成功版本”的指针，旧版本继续可查。

一次缺失、403、超时或不完整扫描不代表下架。只有完整对账中的连续缺失并结合详情页状态，才标记 `unlisted` 或 `unavailable`，同时保留最后成功内容。403 单独标记为访问受阻。

日常运行写本地报告；只有首次完成、源站持续不可用、磁盘不足、失败量明显增加或需要处理认证时才通知。通知渠道在实施阶段选定，不依赖长期打开的聊天维持调度。

## 请求控制与异常恢复

初始建议每个来源域名 1 请求每秒、最多 2 个并发下载，之后以源站限制和小样本结果调整。这是项目的保守起点，不是 LobeHub 或 GitHub 的官方额度。

| 情况 | 行为 |
| --- | --- |
| HTTP 429 或 GitHub 配额耗尽 | 尊重 Retry-After、配额重置时间，暂停对应来源并保留任务；不通过轮换身份规避限制 |
| HTTP 5xx、网络超时 | 带随机抖动的指数退避，单轮最多 5 次，随后进入可重试失败队列 |
| HTTP 401 | 尝试一次正常 token 刷新，仍失败则暂停来源并报告认证问题 |
| HTTP 403 | 区分限流、访问权限和站点拦截；停止盲目重试，不能当作条目不存在 |
| HTTP 404 | 记录失效观察并在后续对账复核，不直接清除本地内容 |
| 数据结构变化 | 保存原始响应、标记解析失败，停止推进该分页检查点 |
| 文件缺失、包损坏或只获得正文 | 标记不完整，保留已有有效快照；不能计入完整下载数 |
| 超大包、文件数或磁盘超过预算 | 暂停对应内容任务，保留目录记录和明确原因；不静默截断后声称完整 |

下载只处理数据，不运行下载内容中的脚本、安装命令或提示词，也不把采集目录放进 `.agents/skills` 或其他自动加载路径。归档解包检查绝对路径、`..` 越界、链接逃逸、压缩比与展开大小；限制 HTTP 重定向目标，拒绝本机、内网和云元数据地址。外部网页引用只记入 manifest，不自动跟随下载。

公开数据集中也可能出现凭证或个人信息，运行日志只记录必要的脱敏错误，不记录 Authorization、cookie 或签名下载 URL 的查询参数。第三方内容的再次公开分发不包含在本阶段范围内。

## 容量与首次运行预算

先对代表性样本测量元数据请求数、仓库复用比例、平均及 P95 包大小、耗时和失败率，再决定全量预算。首页展示数约 33.4 万，足以说明需要断点续传与容量估算，但不能据此承诺完成日期。

估算采用以下模型：

- 请求量约为目录页数，加上需要补充的详情请求、独立仓库或包请求以及重试；同仓库复用可显著减少内容请求。
- 仅作量级示例：若 334,160 条都需要一条详情和一次包下载，则约 66.8 万请求；在同域名每秒 1 请求下，纯请求预算已约 7.7 天，尚未计传输和退避。每条都需要这些请求是估算假设，并非实测。
- 单份内容平均为 100 KiB 时，334,160 份约 31.9 GiB；平均为 1 MiB 时约 326 GiB。原始包、解包、历史版本、缓存和备份还会增加占用，内容去重则可能减少占用。
- 约 33.4 万条、每页 100 条意味着一次完整目录扫描约 3,342 页；实际可用页大小与深分页限制需实测。

实施时先检查服务器可用空间，配置单包上限、总流量上限、单轮时间预算及磁盘保留量。建议磁盘使用达到 80% 时停止新内容下载并报告；已持久化任务可以在释放空间后继续。预算触发必须体现在完成度报告中。

## 分阶段实施与验收

### 阶段一 验证数据源和小样本

在独立配置中接入采集身份，验证无关键词列表、分页参数、稳定排序、总数含义和深分页限制。选取约 100 条代表性样本，覆盖单 Skill 仓库、多 Skill 仓库、子目录、不同许可证、无 GitHub 来源、带附件和失效链接。

验收要求：每条样本都有元数据和明确终态；合格样本能离线读取完整 `SKILL.md` 及附件；版本和来源可回溯；重复运行不重复存储。模拟一次中断后能够恢复，并验证限流退避、异常包隔离及许可证缺失处理。输出认证与接口结论、抽样结果和容量估算后，再开始全量。

### 阶段二 完成首次拉取

实现持久化目录、任务队列、内容快照、断点恢复和 JSONL 导出，然后运行全量任务。交付物包括原始元数据、完整文件树、SQLite 索引、来源 manifest、失败清单和采集报告。实现中的状态查询、恢复、重试命令应写入 README；本方案不将尚未实现的命令写成可用命令。

验收报告至少分别回答：

| 指标 | 定义 |
| --- | --- |
| 目录发现数 | 本轮发现的唯一 `(source, identifier)` 数；附扫描时间范围和分页完整性 |
| 目录覆盖情况 | 与同范围、同时间口径的来源总数对照；拿不到可靠分母时写“未知”，不能填 100% |
| 完整内容数 | `SKILL.md`、约定文件树及 manifest 均校验成功的条目数 |
| 内容获取率 | 完整内容条目数 / 全部已发现条目数；另外单列许可排除后的可采集条目成功率 |
| 去重后内容数 | 按文件树哈希统计的唯一快照数，与条目数、仓库数分开报告 |
| 内容新鲜度 | 距离最近成功检查来源的时间及队列最老等待时间；不能只展示最近程序运行时间 |
| 缺口 | 按许可排除、待许可确认、来源失效、访问受阻、仅正文、校验失败、超预算等逐条列出 |

队列中不存在未解释的 `pending` 或 `running` 才可结束本轮。所有已发现条目必须归入互斥的结果类别，类别数量之和等于条目数。部分条目失败但均有记录，可以叫“首轮执行完成，有缺口”；只有目录边界可靠且范围内内容全部成功，才可叫“该来源范围采集完成”。任何情况下都不把首期成果称为“整个开源社区已全部抓取”。

### 阶段三 启用持续更新

首次全量完成后安装服务器 timer，验证新增、正文变化、附件单独变化、源码先于市场更新、仓库迁移和下架等场景。确认并发锁、恢复、备份与异常通知有效，记录下一次计划运行时间。

全量对账和源码复核是增量更新的组成部分，不能只按照市场排序取前几页。完成一次实际更新周期后，再依据真实吞吐调整频率。

### 阶段四 开展内容分析

采集稳定后再讨论功能分类、相似性、依赖、质量与更新趋势。本阶段只预留原始文件、来源证据、版本与许可证字段，不调用大模型进行大规模分析，不生成向量，不运行 Skill 的功能测试。

长期通过来源适配器接入其他社区目录、作者仓库和 GitHub 发现渠道。每个来源各自维护覆盖率与刷新水位，再通过来源关系和内容哈希关联，逐步扩大社区覆盖。

## 方案确认后的第一步

先实现“数据源认证与分页验证、小样本完整下载、可恢复的本地存储”这条最小链路。通过小样本验收和容量检查后开始首次全量，随后启用持续更新。若官方认证或完整枚举受阻，先解决数据源入口，不能以大量抓取热门页面替代既定目标。
