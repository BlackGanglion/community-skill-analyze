# 社区 Skill 采集与持续更新方案

状态：待确认，尚未实施采集。日期：2026 年 10 月 9 日。

项目目标是建立可追溯、可持续更新的社区 Skill 本地资料库，为后续分类、去重、质量评估和趋势分析提供原始数据。第一阶段以 LobeHub 为发现入口，保存两类资料：**每条 Skill 的元信息，以及它对应源码仓库的全部文件内容**。Skill 通过仓库 ID、版本和仓库内路径关联到源码；分析功能在采集链路稳定后再开展。

本次交付仅为方案文档。采集程序、首次全量下载和定时更新任务将在方案确认后实现。

## 目标与首期边界

“目前开源社区的所有 Skill”是长期覆盖目标，不能用单一市场的收录量证明已经完成。首期可验证的目标是：**尽可能完整地枚举 LobeHub 可访问目录，将 Skill 元信息和对应的完整源码仓库保存到 egg-server 本地，并明确列出未获得完整仓库的条目及原因。**

“本地”默认指现有开发服务器 egg-server，项目目录为 `/home/egg/code/community-skill-analyze`。Mac 用于查看文档和结果，首期不维护第二份自动同步的数据副本。

| 对象 | 首期处理方式 |
| --- | --- |
| LobeHub 可枚举的 Skill 条目 | 保存原始元数据、来源链接、版本、观察时间和采集状态 |
| 可公开获取且许可证允许采集的源码仓库 | 保存选定 commit 下整个仓库的全部文件，包括其他 Skill、业务源码、测试、文档、配置、隐藏文件、二进制资源和许可证，不按 Skill 子目录裁剪 |
| 明确开源的 Skill | 纳入开源分析候选集，保留许可证证据 |
| 非开源、许可证不明确或冲突的条目 | 保留目录记录和状态，默认不进入开源内容集；后续按具体许可决定是否收录内容 |
| 同一仓库中的多个 Skill | 每条 Skill 保留独立元信息，共用一份对应 commit 的完整仓库快照；同仓库不同 commit 分别保存 |
| 不同市场、不同名称或不同仓库中的同源内容 | 保留各自来源关系，使用内容哈希复用相同文件，不合并掉来源身份 |
| 登录受限、私有、付费或已失效内容 | 记录缺口，不尝试绕过访问限制 |
| 历史版本 | 首次保存每个目标 ref 当前对应的完整仓库文件树；从首次采集起保留变化快照，不要求回溯全部提交历史及所有分支 |
| Git LFS 与 submodule | 获取所选 commit 引用的 LFS 实体文件和子模块固定 commit 的文件树；指针未解析或子模块不可访问时标为仓库不完整 |
| Skill 引用的外部网页、依赖和大模型 | 保存引用，不递归抓取外部互联网，不安装依赖、不执行 Skill |

### 完整源码仓库的定义

“全部内容”按选定 commit 的完整文件树验收，不限制文件类型，不省略与目标 Skill 无直接关系的文件。保留文件路径、原始字节、文件模式和符号链接信息；不跟随符号链接读取仓库外部文件。Git LFS 对象和 submodule 在各自来源、权限与预算允许时补齐，缺失项进入 manifest，不能只保存指针却计为完整。

优先跟踪来源明确声明的分支、tag 或 commit；来源没有指定 ref 时使用源仓库默认分支，并保存实际解析的 SHA。首次下载不要求保留全部 `.git` 历史、未引用分支、Issues、PR 讨论、Wiki 或 Release 附件，这些不属于选定版本的源码文件树。一个仓库含有多少 Skill，不影响整仓文件的保存范围。

例如，两个条目分别指向同一仓库的 `skills/pdf` 和 `skills/pptx`，且解析到同一个 commit，则保存两份 Skill 元信息、一份完整仓库快照和两条路径映射。能够离线浏览仓库根目录及所有文件，是本阶段的交付要求。

## 采集路径

推荐采用“市场发现 Skill，按仓库汇总下载，元信息关联完整仓库快照”的流程。

1. **建立目录清单。** 优先通过已验证的官方 Market API 或固定版本的 SDK 获取完整分页结果，保存每页原始响应、参数、总数、页码和观察时间。固定一个 locale，避免多语言页面重复计数。
2. **解析并汇总仓库。** 保存市场 identifier 和原始来源 URL，解析仓库、分支或 tag、Skill 路径，处理仓库转移和 URL 重定向。以托管平台和仓库稳定 ID 归一化身份，汇总同一仓库的所有 Skill，不能根据 slug 中的连字符猜测仓库及目录。
3. **确认内容资格。** 记录仓库、子目录及 Skill 内的 LICENSE、NOTICE、frontmatter 许可声明和市场标签。完整仓库可能包含不同许可证的目录，不能把一个 Skill 的许可推定到整个仓库。缺失或冲突时保留待确认状态；若某部分暂不能获取，整个仓库快照标为不完整。
4. **获取完整仓库快照。** 对合格来源，将各目标 ref 解析为确定的 commit SHA，按 `(repository_id, commit_sha)` 创建一次下载任务。获取完整文件树并补齐 LFS 和 submodule，不使用仅下载 Skill 目录的裁剪策略。下载适配器必须核验文件树完整性，不能仅凭归档解压成功或 Git 命令退出成功就判定完整。
5. **处理缺少源码的条目。** 保存元信息，标记 `repository_missing` 或 `repository_unavailable`。可访问的 Market 发布包可以作为补充资料，单独保存并标记 `package_only`；只有网页正文时标记 `text_only`。两者都不能替代完整源码仓库，也不计入仓库采集成功。
6. **校验并关联。** 将源 commit 的完整 tree 清单与本地文件路径、类型、模式和哈希对账，检查 LFS 实体、子模块 manifest 及 Skill 路径，再关联到各条 Skill。先写临时目录，全部校验通过后原子发布仓库快照；中断和缺失记录不得覆盖上一份完整快照。
7. **输出采集报告。** 分别统计 Skill 元信息数、唯一仓库数、完整仓库快照数、成功关联 Skill 数、文件重复量、失败与排除原因、下载字节数和耗时。

主要交付口径为 `repository_snapshot`，表示所声明 ref 在采集时解析出的完整源码仓库版本；可选的 `market_release` 只表示补充发布包。市场更新时间、Git commit 时间和本地观察时间分别存储。若市场仅指向分支，“最新版”指本次解析到的 SHA，不能宣称它就是市场发布时的源码。仓库树完整但目标 Skill 路径失效时，仓库仍可独立验收，Skill 关联状态必须标为 `skill_path_missing`。

### 全量枚举与完整性

官方说明中的 `--q` 是可选参数，但无关键词查询、深分页上限、排序稳定性和服务器端总数仍需在真实认证后验证。验证失败时暂停全量阶段，保留已发现清单与阻塞原因。

若接口支持稳定游标或快照，则优先使用；若只有页码，采用验证过的稳定排序，记录扫描开始和结束时间及总数变化，对 identifier 去重，并进行重叠扫描与第二轮对账。重复返回同一页、异常空页、总数骤降或缺页都不能视为完成。

目录在扫描期间持续变化时，只能报告某一时间区间内的观测集合。两轮结果相近可以作为收敛信号，不能证明覆盖了整个社区。分类拆分仅在分类覆盖和分页上限经过验证后使用；搜索引擎结果和热门榜不能作为兜底的全量清单。

官方 API 不可用时，可评估已允许且可访问的公开 sitemap 与详情页。报告必须保留 `enumeration_partial` 状态，不能将备用入口发现的集合当成全站全量。若存在官方导出或批量访问渠道，优先使用。

## 本地保存与数据结构

建议首期使用 Python 采集器、SQLite 索引和完整仓库文件快照。每条 Skill 额外导出一份可直接读取的 `metadata.json`，记录仓库快照及 Skill 路径，使资料离开数据库也能解释。该选择便于服务器运行、断点续传和离线分析；它只是采集模块的建议，不限定后续产品界面或分析服务的技术栈。实施时固定依赖版本，先以单机单写入者运行，避免过早引入队列服务和数据库集群。

代码和文档进入 Git；采集到的第三方内容、数据库、缓存、凭证和运行日志不进入当前公开仓库。建议数据根目录独立于代码检出目录，通过 `DATA_DIR` 配置：

```text
/home/egg/data/community-skill-analyze/
  catalog.sqlite
  raw/lobehub/<run_id>/              # 原始目录和详情响应
  skills/<skill_id>/
    metadata.json                   # 独立 Skill 元信息、仓库 ID、快照 ID、Skill 路径
  repositories/<repository_id>/
    metadata.json                   # 仓库 URL、默认分支、跟踪 ref 和来源别名
    snapshots/<commit_sha>/
      manifest.json                 # 完整 tree、文件哈希、LFS 与子模块状态
      files/                        # 整个仓库的完整文件树，可离线浏览
  blobs/sha256/<prefix>/<hash>       # 跨仓库及版本复用相同文件
  supplements/market/<identifier>/  # 可选市场包，不能代替仓库快照
  cache/repos/                      # 可回收的仓库下载缓存
  runs/<run_id>/                    # 检查点、统计和脱敏错误
  exports/                         # 可重建的 JSONL 数据集
```

一个仓库的多个 Skill 通过 `metadata.json` 指向同一份整仓快照，不为每条 Skill 复制全仓。同一仓库的不同 commit 分别保留快照；跨快照相同文件可以复用 blobs。复用时同时保留文件类型和模式，不能仅按字节哈希复用具有不同权限的可写硬链接。对外提供的快照只读，后续分析产物另存，不能修改原始文件。数据库不是唯一副本：Skill 元信息、仓库元信息和快照 manifest 均独立落盘，并定期导出索引。

| 数据实体 | 建议字段与约束 |
| --- | --- |
| 来源条目 `source_entries` | `source`、`identifier` 联合唯一；名称、描述、作者、分类、标签、市场版本、原始 URL、统计值与其观察时间、原始响应位置、首次及最近发现时间 |
| 仓库 `repositories` | 平台和稳定仓库 ID 联合唯一；原始和最终 URL、默认分支、跟踪 ref、许可证证据、首次及最近检查时间；仓库迁移保留别名 |
| Skill 仓库关系 `skill_repositories` | Skill ID、仓库 ID、声明 ref、解析的快照 ID、Skill 路径、映射状态；多个 Skill 可指向一个仓库，一条 Skill 可记录多个明确来源 |
| 仓库快照 `repository_snapshots` | 仓库 ID 与 commit SHA 联合唯一；获取时间、源 tree ID、完整文件树哈希、LFS 和子模块清单及状态、完整性状态、manifest 路径、采集器版本 |
| 文件 `files` | 仓库快照、相对路径、类型、模式、大小、原始字节哈希、blob 路径；完整 tree 哈希覆盖全部路径、类型、模式及内容，Skill 之外的文件变化也生成新版本 |
| 补充发布包 `market_packages` | 来源 identifier、市场版本、包哈希、获取时间与文件清单；与完整仓库快照分别统计 |
| 采集任务 `jobs` | 稳定任务键、状态、尝试次数、下次重试时间、错误分类、租约及检查点；同一任务重复执行不产生重复快照 |
| 运行 `runs` | 类型、起止时间、配置与采集器版本、目录边界、分项计数、流量、完整性结论、上次成功时间 |

缺失字段保存为 null，并与空字符串、0 区分。统计字段不参与内容哈希。市场名称不作为文件路径或唯一主键；路径使用内部安全 ID，原始名称保存在元数据中。

## 持续更新设计

建议首次全量采集完成后，在 egg-server 上由 systemd timer 启动采集命令。以下是计划频率，本次不创建 timer、cron 或 Codex 自动化。

| 周期 | 任务 | 更新策略 |
| --- | --- | --- |
| 每日北京时间 03:00 | 目录变化扫描 | 按 `updatedAt` 倒序读取，覆盖上次成功水位前 48 小时；相同时间戳继续遍历完整边界；只有接口稳定性通过验证后才允许提前停止 |
| 每日 | 仓库更新队列 | 优先处理新增仓库和变化条目；按仓库汇总目标 ref，SHA 未变化则复用快照，变化则获取整仓新快照，并更新所有相关 Skill 的映射；源码检查独立于市场更新时间 |
| 每周日北京时间 04:00 | 全目录对账 | 完整重扫 identifier，发现漏项、来源变化、市场下架和增量扫描遗漏 |
| 滚动七天 | 未变化来源复核 | 对所有可跟踪的仓库 ref 分批重新检查；固定 commit 仅复核可用性，未补齐的 LFS 和子模块进入独立重试队列 |
| 每周 | 数据保护与恢复检查 | 一致性备份数据库、Skill 和仓库元信息、manifest 与不可变 blobs；备份目的地和容量在实施阶段确定 |

七天复核是待容量验证的目标，不是现阶段承诺。若吞吐不足，报告队列年龄和预计滞后并调整周期，不静默将旧数据标为最新。首次全量持续数天时，应同时登记新增条目，避免首次扫描结束前数据已经大幅落后。

更新任务与首次采集共享同一任务队列和锁，防止重叠运行。上一轮未结束时不再启动第二个全量任务；中断任务恢复租约后继续。目录水位只有在相关记录与后续任务持久化后才能推进，内容下载失败由队列独立重试。

能确认服务端支持时使用 ETag 或 Last-Modified 条件请求；不能用 HTTP 200 或版本字符串未变代替内容哈希校验。以仓库 commit 检测变化，保留每个新 commit 的整仓 manifest 并复用相同文件；整仓校验成功后才更新该 ref 的“最新成功版本”及 Skill 映射，旧版本继续可查。即使 `SKILL.md` 没变，只要仓库其他文件变化，也要保存对应的新仓库快照。固定 tag 或 commit 的 Skill 不随默认分支自动改绑。

一次缺失、403、超时或不完整扫描不代表下架。只有完整对账中的连续缺失并结合详情页状态，才标记 `unlisted` 或 `unavailable`，同时保留最后成功内容。403 单独标记为访问受阻。

日常运行写本地报告；只有首次完成、源站持续不可用、磁盘不足、失败量明显增加或需要处理认证时才通知。通知渠道在实施阶段选定，不依赖长期打开的聊天维持调度。

## 请求控制与异常恢复

初始建议每个来源域名 1 请求每秒、最多 2 个并发下载，之后以源站限制和小样本结果调整。这是项目的保守起点，不是 LobeHub 或 GitHub 的官方额度。

| 情况 | 行为 |
| --- | --- |
| HTTP 429 或 GitHub 配额耗尽 | 尊重 Retry-After、配额重置时间，暂停对应来源并保留任务；不通过轮换身份规避限制 |
| HTTP 5xx、网络超时 | 带随机抖动的指数退避，单轮最多 5 次，随后进入可重试失败队列 |
| HTTP 401 | 尝试一次正常 token 刷新，仍失败则暂停来源并报告认证问题 |
| HTTP 403 | 区分限流、访问权限和站点拦截；停止盲目重试，不能当作条目不存在 |
| HTTP 404 | 记录失效观察并在后续对账复核，不直接清除本地内容 |
| 数据结构变化 | 保存原始响应、标记解析失败，停止推进该分页检查点 |
| 仓库文件缺失、LFS 未补齐或子模块不可访问 | 仓库标记不完整，记录具体缺失清单并保留上一份完整快照；不能计入完整仓库数 |
| 只有市场包或正文，缺少源码仓库 | 分别标记 `package_only` 或 `text_only`，仍列入源码仓库获取缺口 |
| 超大仓库、文件数或磁盘超过预算 | 暂停对应仓库任务及相关 Skill 的完成状态，保留具体原因；不得自动缩减为仅下载 Skill 子目录 |

下载只处理数据，不运行下载内容中的脚本、安装命令、Git hooks、自定义过滤器或提示词，也不把采集目录作为 agent 工作目录或注册到自动加载路径。整仓中原有的 `.agents/skills`、`AGENTS.md` 等文件仍完整保存，但仅作为分析数据。归档解包检查绝对路径、`..` 越界、链接逃逸、压缩比与展开大小；限制 HTTP 重定向、LFS 与子模块来源，拒绝本机、内网和云元数据地址。递归子模块按固定 commit 去重并检查循环，预算或安全限制导致中止时明确记录仓库不完整。外部网页引用只记入 manifest，不自动跟随下载。

公开数据集中也可能出现凭证或个人信息，运行日志只记录必要的脱敏错误，不记录 Authorization、cookie 或签名下载 URL 的查询参数。第三方内容的再次公开分发不包含在本阶段范围内。

## 容量与首次运行预算

先对代表性样本测量元数据请求数、唯一仓库数、每仓库 Skill 数、目标 ref 数、整仓展开大小、LFS 与子模块大小、耗时和失败率，再决定全量预算。首页展示数约 33.4 万，不能据此推算仓库数或总空间；容量必须根据完整仓库的实测大小计算，不能用单个 Skill 包的平均大小代替。

估算采用以下模型：

- 请求量约为目录页数，加上需要补充的 Skill 详情请求、唯一仓库目标版本的发现与下载请求、LFS 对象和子模块请求以及重试。同一仓库同一 commit 只下载一次。
- 主数据容量约为所有唯一仓库快照的文件字节总量，加上 LFS、子模块、元信息和 manifest；再扣除实际去重收益。历史快照、Git 下载缓存、临时文件和备份单独计算，不能把它们当成零成本。
- 仅作量级示例：若有 10,000 个唯一仓库，每个完整快照平均展开大小为 100 MiB，仅一轮文件树约 976.6 GiB；若平均为 1 GiB，则约 9.77 TiB。仓库数和均值均为假设，并非实测；LFS 和子模块若未计入均值还需另加。
- 初次采样报告同时列出平均值、P50、P95、最大仓库大小与可用空间，按仓库大小分层估算；不能只抽取热门小 Skill 后直接外推全部仓库。
- 约 33.4 万条、每页 100 条意味着一次完整目录扫描约 3,342 页；实际可用页大小与深分页限制需实测。

实施时先检查服务器可用空间，配置单仓库预算、总流量上限、单轮时间预算及磁盘保留量。建议磁盘使用达到 80% 时停止新仓库下载并报告；已持久化任务可以在扩容或释放空间后继续。超预算仓库保留待处理状态，不因体积大而永久跳过或裁剪内容；所有预算触发必须体现在完成度报告中。

## 分阶段实施与验收

### 阶段一 验证数据源和小样本

在独立配置中接入采集身份，验证无关键词列表、分页参数、稳定排序、总数含义和深分页限制。选取约 100 条代表性 Skill 样本，按唯一仓库下载，覆盖单 Skill 仓库、多 Skill 仓库、大型仓库、子目录、隐藏文件、二进制文件、LFS、子模块、不同许可证、无源码来源和失效链接。

验收要求：每条样本都有独立元信息文件和明确终态；对应仓库能离线浏览完整文件树，且与固定 commit 的 tree 清单对账通过；LFS 实体和子模块均有校验结果；同仓库多个 Skill 共用快照但元信息保持独立。验证仓库根目录、Skill 之外的源码、测试和隐藏文件均未被过滤，版本和来源可回溯，重复运行不重复存储。模拟一次中断后能够恢复，并验证限流退避、异常包隔离及许可证缺失处理。输出认证与接口结论、抽样结果和整仓容量估算后，再开始全量。

### 阶段二 完成首次拉取

实现持久化目录、按仓库去重的任务队列、完整仓库快照、Skill 元信息映射、断点恢复和 JSONL 导出，然后运行全量任务。交付物包括原始元数据、每条 Skill 的 `metadata.json`、完整源码仓库文件树、SQLite 索引、仓库 manifest、失败清单和采集报告。实现中的状态查询、恢复、重试命令应写入 README；本方案不将尚未实现的命令写成可用命令。

验收报告至少分别回答：

| 指标 | 定义 |
| --- | --- |
| 目录发现数 | 本轮发现的唯一 `(source, identifier)` 数；附扫描时间范围和分页完整性 |
| 目录覆盖情况 | 与同范围、同时间口径的来源总数对照；拿不到可靠分母时写“未知”，不能填 100% |
| 完整仓库数与快照数 | 分别统计具有完整快照的唯一仓库数及 `(repository_id, commit_sha)` 数，要求全 tree、LFS、子模块与 manifest 校验通过 |
| 仓库获取率 | 完整仓库目标版本数 / 已发现的仓库目标版本数；另列许可排除后成功率；无源码条目单列并计入 Skill 关联成功率的分母 |
| Skill 关联成功率 | 元信息齐全、所声明源码目标均关联完整仓库快照且 Skill 路径有效的条目数 / 全部已发现条目数；没有源码的条目仍计入分母 |
| 存储复用 | 仓库复用的 Skill 数、文件内容去重前后字节数；不能把不同来源仓库的同哈希文件树当成同一来源 |
| 内容新鲜度 | 距离最近成功检查来源的时间及队列最老等待时间；不能只展示最近程序运行时间 |
| 缺口 | 按许可排除、待许可确认、无源码仓库、来源失效、访问受阻、仅市场包、仅正文、Skill 路径失效、LFS 或子模块不完整、校验失败、超预算等逐条列出，并关联受影响的全部 Skill |

队列中不存在未解释的 `pending` 或 `running` 才可结束本轮。所有已发现条目必须归入互斥的结果类别，类别数量之和等于条目数。部分条目失败但均有记录，可以叫“首轮执行完成，有缺口”；只有目录边界可靠且范围内内容全部成功，才可叫“该来源范围采集完成”。任何情况下都不把首期成果称为“整个开源社区已全部抓取”。

### 阶段三 启用持续更新

首次全量完成后安装服务器 timer，验证新增、正文变化、Skill 之外的源码变化、LFS 和子模块变化、源码先于市场更新、仓库迁移和下架等场景。特别验证同仓库多个 Skill 只触发一次对应版本下载，整仓完成后再更新各条映射。确认并发锁、恢复、备份与异常通知有效，记录下一次计划运行时间。

全量对账和源码复核是增量更新的组成部分，不能只按照市场排序取前几页。完成一次实际更新周期后，再依据真实吞吐调整频率。

### 阶段四 开展内容分析

采集稳定后再讨论功能分类、相似性、依赖、质量与更新趋势。本阶段只预留原始文件、来源证据、版本与许可证字段，不调用大模型进行大规模分析，不生成向量，不运行 Skill 的功能测试。

长期通过来源适配器接入其他社区目录、作者仓库和 GitHub 发现渠道。每个来源各自维护覆盖率与刷新水位，再通过来源关系和内容哈希关联，逐步扩大社区覆盖。

## 方案确认后的第一步

先实现“数据源认证与分页验证、Skill 元信息落盘、按仓库去重的整仓下载、可恢复的本地存储”这条最小链路。通过小样本验收和整仓容量检查后开始首次全量，随后启用持续更新。若官方认证或完整枚举受阻，先解决数据源入口，不能以大量抓取热门页面替代既定目标。
